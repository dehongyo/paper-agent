# Paper Agent 阶段二设计：文献工作台 + 可溯源 RAG + 轻量论文检索

## 摘要

阶段二的目标，是把阶段一已经跑通的“上传 PDF、自动摘要、单篇论文问答”升级成一个真正可用的科研文献工作台。

阶段二按三层推进：

1. 强化本地文献库：支持论文元数据编辑、标签、笔记、删除、筛选和关键词检索。
2. 升级 RAG：从“单篇论文问答”扩展到“跨本地文献库问答”，并且答案必须带来源证据。
3. 增加轻量外部论文检索：接入 arXiv 和 Semantic Scholar，只展示论文名、作者、摘要、年份和直达链接。

外部检索在阶段二只做轻量入口。系统不下载外部 PDF，不绕过出版商页面，不抓取 Google Scholar，也不自动把搜索结果导入本地文献库。

## 目标

- 让文献库从“上传列表”变成可日常使用的研究资料库。
- 让用户能维护本地论文的标题、作者、DOI、来源链接、发表日期、摘要、标签和笔记。
- 支持按关键词、状态、标签筛选本地论文。
- 支持跨所有本地论文片段的语义检索。
- 让 RAG 回答能附带来源论文和原文片段，降低幻觉风险。
- 增加外部论文检索页，通过 arXiv 和 Semantic Scholar 找论文，并提供直达链接。
- 保持阶段二可分步交付，每一层都能独立验证。

## 非目标

- 不自动下载外部 PDF。
- 不自动导入外部搜索结果。
- 不抓取 Google Scholar。
- 不做引用图谱、参考文献格式化或 Zotero 集成。
- 不做多智能体编排。
- 不做完整论文编辑器或综述写作流程。
- 不做用户账号、多租户或权限系统。

## 当前基础

阶段一已经具备：

- 后端：`paper-agent-backend`，Spring Boot。
- 前端：`paper-agent-frontend`，React/Vite。
- PDF 上传接口：`POST /api/papers/upload`。
- 本地论文列表接口：`GET /api/papers`。
- 单篇论文详情接口：`GET /api/papers/{id}`。
- 论文全文接口：`GET /api/papers/{id}/fulltext`。
- 单篇论文流式问答接口：`POST /api/chat/stream`。
- 数据表：`papers` 和 `paper_chunks`，其中 `paper_chunks` 已保存 pgvector 向量。

阶段二应尽量保持现有接口兼容，在此基础上做增量扩展。

## 用户体验设计

### 文献库

文献库页面升级为更高密度的工作台：

- 顶部操作：上传 PDF、刷新、关键词搜索。
- 筛选条件：状态、标签、日期、文本关键词。
- 论文卡片或列表项展示：标题、作者、文件名、标签、状态、创建日期、摘要预览。
- 每篇论文支持操作：查看详情、编辑元数据、编辑笔记和标签、基于该论文提问、删除。
- 详情视图展示：元数据、摘要、笔记、标签，以及相关证据片段。

页面仍然要适合少量论文时的轻量使用，但也要能支撑几十篇论文的扫描和管理。

### 可溯源 RAG

聊天页面支持两种问答范围：

- 当前论文：只基于选中的单篇论文回答。
- 全部文献库：基于本地所有就绪论文回答。

AI 回答下方展示紧凑的证据区域。每条证据包含：

- 来源论文标题。
- 原文片段摘录。
- 相似度分数或排序。
- 论文 ID，用于跳转或选择该论文继续对话。

如果没有检索到足够相关的证据，助手应明确说明“本地文献库中没有足够信息”，而不是凭空回答。

### 外部论文检索

新增“论文检索”或“发现”页面。

搜索结果展示：

- 论文标题。
- 作者。
- 年份或发表日期。
- 来源，例如 arXiv 或 Semantic Scholar。
- 摘要片段。
- 直达链接，例如论文页面、DOI、arXiv 页面，或 API 已提供的 PDF 链接。

搜索结果不下载、不自动入库。结果只提供“打开链接”操作，在新浏览器标签页访问外部页面。用户如果想加入本地文献库，需要自己下载 PDF，然后通过现有上传流程上传。

## 后端设计

### 数据模型

扩展 `papers` 表：

- `doi VARCHAR(255)`
- `source_url VARCHAR(1000)`
- `published_at DATE`
- `notes TEXT`
- `tags TEXT`

标签的第一版建议用 `TEXT` 保存，后端对外统一暴露为字符串数组。这样实现简单，也方便以后无痛迁移到独立 `paper_tags` 表。

证据检索需要从 `paper_chunks` 返回更多信息：

- `paper_chunks.id`
- `chunk_index`
- `content`
- `paper_id`
- 来源论文标题
- 相似度分数

### API 接口

本地文献库：

- `GET /api/papers?query=&status=&tag=`
  - 返回筛选后的论文列表。
- `PATCH /api/papers/{id}`
  - 更新标题、作者、DOI、来源链接、发表日期、摘要、笔记和标签。
- `DELETE /api/papers/{id}`
  - 删除论文记录、分块记录，并尽量删除本地文件。
- `GET /api/papers/tags`
  - 返回所有已使用标签，用于筛选。

语义检索：

- `POST /api/search/semantic`
  - 请求：`{ "query": "...", "paperId": 123 | null, "limit": 8 }`
  - `paperId` 为空时，在全部就绪论文中检索。
  - 返回结构化证据片段，包含论文元数据和相似度。

可溯源问答：

- 扩展 `POST /api/chat/stream` 请求，增加 `scope`。
  - `scope: "paper"`：使用 `paperId` 做单篇论文问答。
  - `scope: "library"`：在全部就绪论文中检索证据。

为了更容易测试和展示引用，阶段二建议新增一个非流式接口：

- `POST /api/chat/rag`
  - 返回：`{ answer, evidence[] }`
  - 它可以和现有 SSE 流式接口共存。

外部论文检索：

- `GET /api/discovery/search?query=&source=&limit=`
  - `source` 可选值：`all`、`arxiv`、`semantic-scholar`。
  - 返回统一格式的外部搜索结果。

### 服务划分

新增或扩展以下服务：

- `PaperService`
  - 负责元数据更新、删除、筛选、标签管理。
- `EvidenceSearchService`
  - 负责单篇或全库语义检索。
  - 返回结构化证据，而不是只返回纯文本片段。
- `TraceableChatService` 或扩展 `ChatService`
  - 根据证据构造提示词。
  - 返回答案和证据列表。
- `DiscoveryService`
  - 聚合外部论文源。
- `ArxivClient`
  - 调用 arXiv API，并解析 Atom XML。
- `SemanticScholarClient`
  - 调用 Semantic Scholar paper search API。

### RAG 提示词规则

可溯源 RAG 的提示词必须约束模型：

- 只基于提供的证据回答。
- 证据不足时要明确说明。
- 不编造论文标题、作者、实验数据或引用。
- 默认使用简洁中文回答。
- 在回答中使用 `[1]`、`[2]` 等稳定编号引用证据。

论文标题、chunk id、来源链接、相似度等结构化信息应由后端服务附加，不依赖模型自己生成。

## 前端设计

### 类型定义

新增 TypeScript 类型：

- `PaperUpdateRequest`
- `PaperDetail`
- `EvidenceChunk`
- `SemanticSearchRequest`
- `SemanticSearchResponse`
- `TraceableChatResponse`
- `DiscoveryResult`

### 文献库页面

页面需要增加状态：

- 搜索关键词。
- 当前状态筛选。
- 当前标签筛选。
- 论文列表。
- 编辑弹窗或侧边面板状态。
- 删除确认状态。

继续沿用现有视觉风格。操作按钮尽量使用 lucide 图标。列表和卡片要偏工作台风格，信息密度高一些，避免做成宣传页。

### 聊天页面

增加问答范围控制：

- 当前论文。
- 全部文献库。

当接口返回证据时，在答案下方渲染来源块。来源块应能点击，用于打开论文详情或切换到该论文继续提问。

### 论文检索页面

侧边栏新增“论文检索”入口。

页面包含：

- 搜索框。
- 来源选择器。
- 结果列表。
- 外部链接按钮。

页面文案要明确：这些是外部链接，不是本地文献库条目。阶段二不要出现“导入”“下载”这类会误导用户的主操作。

## 数据流

### 本地文献库管理

1. 用户编辑论文元数据、笔记或标签。
2. 前端发送 `PATCH /api/papers/{id}`。
3. 后端校验并更新论文。
4. 前端刷新对应论文条目。

### 跨文献库语义检索

1. 用户发起全库问题或语义检索。
2. 后端对查询文本向量化。
3. 后端检索 `paper_chunks`，可选按 `paper_id` 过滤。
4. 后端关联 `papers` 元数据。
5. 后端返回排序后的证据片段。

### 可溯源 RAG

1. 用户提问。
2. 后端检索证据。
3. 如果证据不足，后端返回证据不足提示。
4. 如果有证据，后端用证据和严格约束构造提示词。
5. 后端返回答案和证据列表。
6. 前端同时展示答案和来源。

### 外部论文检索

1. 用户输入查询词。
2. 后端查询 arXiv 和/或 Semantic Scholar。
3. 后端统一结果格式。
4. 前端展示结果和外部链接。
5. 用户手动打开链接。

## 错误处理

- 论文 ID 不存在时返回 404。
- 更新字段非法时返回 400，并给出可读错误。
- 删除论文时，如果本地文件已不存在，不应阻塞数据库清理。
- 语义检索失败时，返回空结果和错误信息，不应导致聊天崩溃。
- 外部 API 失败要按来源处理：如果 arXiv 失败但 Semantic Scholar 成功，可以返回部分结果和警告。
- 外部检索要设置超时和较小的默认 limit，避免 UI 长时间等待。

## 测试策略

后端测试：

- 论文更新能正确保存元数据、标签和笔记。
- 删除论文会删除论文记录和分块记录。
- 文献库筛选能返回预期记录。
- 语义检索能返回带论文元数据的证据。
- 全库检索不需要 `paperId`。
- arXiv 和 Semantic Scholar 客户端能解析代表性响应。
- 某个外部源失败时，发现服务能返回部分结果。
- 可溯源问答能返回证据，并能处理证据不足场景。

前端测试，如果当前项目测试工具允许：

- 文献库筛选会按预期参数调用 API。
- 编辑表单会提交正确 patch payload。
- 删除确认成功后，列表移除对应论文。
- 聊天证据块能展示来源标题。
- 外部检索结果能展示外部链接。

手动验证：

- 上传或复用至少两篇本地 PDF。
- 给不同论文添加不同标签和笔记。
- 按标签和关键词筛选。
- 向全部文献库提问，确认来源来自正确论文。
- 搜索一个外部研究主题，并打开结果链接。

## 推进顺序

1. 数据与 API 基础
   - 扩展 schema 和 DTO。
   - 增加论文更新、删除、标签和筛选接口。
2. 文献库 UI
   - 增加搜索和筛选控件。
   - 增加编辑和删除流程。
3. 证据检索
   - 增加结构化语义检索服务和接口。
   - 保持旧的单篇 RAG 可用。
4. 可溯源 RAG
   - 增加答案加证据接口。
   - 在聊天 UI 中展示来源。
5. 轻量外部检索
   - 增加外部检索客户端和统一接口。
   - 增加只展示直达链接的检索页面。

## 验收标准

- 用户可以编辑论文标题、作者、笔记、标签、DOI、来源链接和发表日期。
- 用户可以删除论文和对应 chunks。
- 用户可以按关键词、状态和标签筛选文献库。
- 用户可以跨全部就绪论文做语义检索。
- 用户可以向全部文献库提问，并得到带来源证据的回答。
- 证据不足时，答案不会编造来源。
- 用户可以在 UI 中搜索 arXiv 和 Semantic Scholar。
- 外部搜索结果只展示直达链接，不下载、不自动入库。
- 阶段一已有上传和单篇论文问答流程继续可用。

## 保留的实施选择

阶段二唯一需要在实施计划里最终落定的选择，是标签存储方式：

- 简化方案：`papers.tags` 保存为文本，对外暴露为数组。
- 规范方案：新增 `paper_tags` 表。

推荐第一版使用简化方案，因为它足够支撑阶段二功能，且 API 可以保持数组形式，未来再迁移到独立标签表也不会影响前端契约。
